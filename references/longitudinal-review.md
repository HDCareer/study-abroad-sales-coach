# 跨周客户续接与销售带教观察

用户要求每天/每周连续复盘、查看上期跟回结果、同一销售的重复问题或训练后变化时使用。本机制读取获准保存的结构化快照，不靠模型永久记忆，不要求建立CRM。首次没有历史时建立观察基线，不编造趋势。

## 先区分两种管理用途

**客户状态续接：** 谁仍在推进，哪位客户从待判变有效、已付试听、已完课或已正式购买，上次待办现在是否有新结果。同一人换了周或批次编号不自动变新客。跟进优先级依据本机构实际业务周期，不自动推翻有效性或放弃仍有明确约定、付款/试听进展的客户。退出当前追单名单不等于流量无效，也不抹掉已发生的销售过程。

**销售带教观察：** 同样的销售机会出现几次，哪几次没接住，训练后出现的新机会处理得怎样。客户不再活跃，其历史销售动作仍可能有带教价值。它不要求长期保留完整聊天；只留汇总能观察趋势，但源资料到期后无法重新核查原话。去掉姓名的哈希标识仍可关联，不等于真正匿名，不能因此绕过保留期限。

按本机构实际带教周期设计观察长度；资料与结构化档案的范围和期限须有明确授权，不默认长期保存，也不因功能新增改变原政策。

## 身份、需求与重复计数

- 来源账号ID+来源客户ID确定销售与客户的承接关系；批次案例编号、昵称、头像或学校不能用作跨批唯一身份。来源ID未能确认时单批照常分析，跨周列“身份未能续接”，不强行匹配。
- 一个客户的不同课程需求或重新开始的咨询，要有明确且稳定的需求ID。已有需求ID沿用，不每周新编；只有客户关系ID而无需求ID时，仅跟踪关系当前状态，不能声称已分清多笔销售机会。转接、家长与学生、多个账号之间只在有可核查映射时关联，本地工具不按相似昵称自动合并。
- 同周多次全量导出只保留该周最新资料截止的快照作为该周输入，不相加；增量消息须先由上游归并成完整可见输入。相同截止时间的修正版须注明替代的analysis_id。旧批被替代不计第二次失败。
- 同一问题跨周尚未解决，计为原观察的延续，不每周新增一次缺口。只有实际出现新的客户决定/回应机会并有新的消息锚点，才计新机会。不能把销售后来的补救、客户最终付款，当作原先动作本来没有缺口。

## 机会定义与训练观察

定义稳定的同类机会key、定义版本、业务规则版本、层次、阶段和适用条件，例如“客户直接问费用且销售有回应机会”。相同版本下定义不能改写；定义或业务规则变化时分段观察，不把不同标准混成改善。

每项观察以原始消息作稳定锚点。优先用来源消息ID；没有时，以消息时间、可核实角色和原文的摘要识别，导出文件名/行号变化不应新增事件。同一时间相同消息重复且无稳定ID时，先核查身份与顺序，不能猜成两个或强合一个。代码只做机械去重，是否真属同一销售机会由Skill读上下文判断。

观察分gap/sound/unknown，复核状态另分unreviewed/confirmed/contested/withdrawn。unknown、申诉待核、已撤销不进入可判断分母；未人工复核的数量单独列出，不称为已确认的能力缺陷。人工纠错替换同一观察；未确认的矛盾结果先标冲突，不择取更差或更好的那一份。

培训建议和实际执行分开。现有plans仍是proposed；实际布置、完成、验收另记事件与真实确认来源。没有完成依据，不写“已训练仍不会”；完成后没有新的同类机会，不写“没有改善”。训练前后按机会实际发生时间划分，不按上传时间；同一旧错误反复导出或后来修复，不充当训练后的新样本。即使问题比例下降，也只描述可见变化，不直接证明训练因果或作岗位淘汰结论。

## 主管应先看到什么

默认简短呈现：本期发生了哪些客户状态变化；每位销售各类问题的“缺口/可判断机会”、待核和未复核数量；哪项实际训练后有了新机会及表现；哪些客户仍需跟进。相同机会只计一次，首次观察客户数不冒充真正新增客户数。缺历史、同类样本不足、标准变更和原证据不可回查要明确说明。

当前跨周表为独立的本地观察表，与单批简明报告并用。原案通过当前analysis_id、案例编号和获准保留的来源定位；结构化快照不复制原话，工具不自动跨文件打开已过期证据，也不承诺已经接到探马后台。

## 数据与运行

在原分析的`management.longitudinal`中给`definitions`和`training_events`，每案`management.tracking`给`opportunity_id`（未知null）与`events`。同一分析经校验后由[统一管理结果](review-results.md)保留这些字段，再生成跨周快照。历史输入没有这些字段仍兼容；只能续接状态，不能凭空统计同类能力变化。

definition包含`key/version/policy_version/label/opportunity_definition/layer/stage`。event包含相同前三项、`state/review/change_kind/anchor_ref/observed_at`；change_kind为observation/correction，人工确认或撤销、正式纠错需`confirmation_source`。training_event含`id/plan_id/key/version/policy_version/kind/at/confirmation_source`，kind为assigned/completed/verified。确认来源记录真实材料位置，程序不能认证人员权限；按[复核规则](appeals-and-review.md)核验。

```text
python scripts/longitudinal_review.py --results <本期统一结果.json> --history <上期快照.json> --snapshot-output <本期快照.json> --summary-output <跨周结果.json> --output <跨周观察.html> --recorded-at <登记时间> --retention-start-at <原授权起算时间>
```

只使用Python标准库。快照写入授权私有目录，不进入Skill、GitHub或公共样例；只保留关联摘要、阶段、观察类型、时间、计数和执行状态，原身份ID、客户姓名及聊天原文不进入快照。留存的销售身份和可关联客户标识仍须按授权管理。

必须配置本机构已授权的保留期限，不因重导入、修正版或重新生成而顺延原保留期。获公司明确授权后才可通过`--retention-days`和`--retention-basis`设定结构化档案期限；不能仅凭参数声称已获授权，完整聊天和报告的政策不随之改变。快照到期后停止参与比较并列到期待处理，不自动删文件；实际删除仍按现行项目规则核对并取得具体对象批准。到期后不能偷偷把原记录复制到新快照延长保留。

规则版本、快照与分析编号可作为工程证据长期保留，但保留可重新识别客户或员工的管理档案须有相应授权。若只需长期团队汇总，后续可另作去除客户关联的汇总设计；当前不把本快照声称为匿名汇总或已实现长期员工画像。
